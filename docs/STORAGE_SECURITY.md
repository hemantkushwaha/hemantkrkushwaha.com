# Storage Security & Access Layer Architecture

**Hemant Kumar Kushwaha Knowledge Platform (`hemantkrkushwaha.com`)**  
**Architecture Specification: Step 12 — Storage Security & Access Layer**

---

## 1. Why `content-files` is a Private Bucket

In the Hemant Kumar Kushwaha Knowledge Platform, academic lecture materials, research preprints, philosophical essays, and educational slide decks represent curated intellectual property.

1. **Defense in Depth**: Making the Supabase Storage bucket `content-files` private (`public: false`) ensures that no binary object can be fetched directly via standard public CDN endpoints without prior authorization.
2. **Revocability**: If an article or resource is moved from `published` to `draft` or `archived`, public URLs cannot be invalidated easily if cached by third parties. With a private bucket and short-lived signed URLs, revocation is effective immediately.
3. **Auditability & Traffic Control**: All requests for files transit through application security checks, preventing unmetered scraping or unauthorized direct file linking.

---

## 2. Why Public Storage URLs are Forbidden

Public storage URLs in object storage systems persist indefinitely. Using public URLs creates severe security vulnerabilities:

- **Bypassing Content State Changes**: A file uploaded for public viewing would remain permanently downloadable even if the content record is unpublished, archived, or deleted.
- **Bypassing Tier Restrictions**: Public URLs cannot enforce membership or premium access boundaries because anyone with the URL can share it.
- **Predictable Asset Scraping**: Deterministic storage paths (e.g., `academics/computer-networks/arp/study-material/arp-lecture-notes.pdf`), while optimal for organization, would become trivially scrapable if the bucket were public.

By enforcing private bucket settings and strictly using signed URLs, the platform guarantees that every file access is validated at the moment of request.

---

## 3. Temporary Signed URLs & Expiration Lifecycle

Signed URLs are cryptographically authenticated query strings generated server-side using the Supabase `service_role` secret.

- **Cryptographic Signature**: The signed URL contains a time-limited HMAC signature generated by Supabase Storage.
- **Default TTL**: 900 seconds (15 minutes).
- **Safety Bounds**: The system strictly clamps requested expirations between `60` seconds (minimum) and `86,400` seconds (24 hours maximum).
- **Metadata Returned**:
  ```json
  {
    "success": true,
    "signedUrl": "https://<supabase-url>/storage/v1/object/sign/content-files/academics/...",
    "expiresIn": 900,
    "expiresAt": "2026-09-18T10:15:00.000Z",
    "fileName": "arp-lecture-notes.pdf"
  }
  ```
- **Automatic Invalidation**: Once `expiresAt` passes, requests to the signed URL return HTTP `403 Forbidden` directly from Supabase Storage.

## 4. Visibility-Based Access Control Model

Access to content files is governed by two relational dimensions: **Publication Status** and **Content Visibility**.

| Publication Status | Visibility Level | Anonymous Public | Registered User | Premium User | HTTP Status |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `draft` | *Any* | **Denied** | **Denied** | **Denied** | `403 Forbidden` (`DRAFT_PROTECTED`) |
| `archived` | *Any* | **Denied** | **Denied** | **Denied** | `403 Forbidden` (`ARCHIVED_PROTECTED`) |
| `published` | `public` | **Allowed** | **Allowed** | **Allowed** | `200 OK` |
| `published` | `registered` | **Denied** | **Allowed** | **Allowed** | `401 Unauthorized` (if unauthenticated) |
| `published` | `premium` | **Denied** | **Denied** | **Allowed** | `401 Unauthorized` / `403 Forbidden` |

### Path Verification Check
When an API request includes a `path` parameter, the service compares `path` against the canonical file path stored in the database record. If a mismatch is detected, the request is rejected immediately with `400 Bad Request` (`INVALID_STORAGE_PATH`), preventing attackers from swapping identifiers to download unauthorized files.

---

## 5. Clean Premium Authorization Boundary

To comply with the project rule prohibiting premature feature development (no unrequested payment gateways, fake subscriptions, or mock billing engines):

- Premium authorization is implemented as a clean interface contract (`AccessUser.hasPremiumAccess`).
- The security layer inspects whether the caller's verified user context possesses `hasPremiumAccess: true`.
- If unauthenticated, it returns `401 Unauthorized`.
- If authenticated but unauthorized, it returns `403 Forbidden`.
- When real membership or authentication systems are introduced in future steps, the boundary will integrate seamlessly without requiring rewrites of the storage security layer.

---

## 6. Separation of Concerns: Database RLS vs Storage Security

The system employs two distinct security perimeters:

1. **PostgreSQL Row Level Security (RLS)**:
   - Governs access to relational metadata rows in `content`, `tags`, and `content_relationships`.
   - Ensures queries only return metadata rows appropriate for the client.
2. **Supabase Storage Object Security**:
   - Governs physical binary assets stored in `storage.objects`.
   - Even if an attacker learns a valid binary storage path, storage RLS policies prevent direct download or modification.
   - Access to the binary asset is granted only when the server generates a signed URL after evaluating both the database record and user credentials.

---

## 7. Zero Secret Leakage Mandate

- `SUPABASE_SECRET_KEY` is loaded strictly in server-side modules (`src/server/lib/supabaseServer.ts`).
- Client-side code and build bundles only have access to `VITE_SUPABASE_PUBLISHABLE_KEY`.
- All storage write operations (`uploadFile`, `deleteFile`) and signed URL generations run server-side.
- Error messages sent to clients are sanitized into standardized error codes (`DRAFT_PROTECTED`, `UNAUTHORIZED`, `FORBIDDEN`, `INVALID_STORAGE_PATH`) and never expose SQL statements, internal file systems, or Supabase credentials.
